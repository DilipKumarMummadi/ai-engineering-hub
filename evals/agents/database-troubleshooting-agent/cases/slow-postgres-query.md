# Scenario

A login lookup in a .NET service backed by PostgreSQL has become slow as the users table grew. The developer says "we already have an index on email, so the database must be underpowered". The team asks the Database Troubleshooting Agent to investigate.

# Input

Our login lookup by email takes over 2 seconds now. We already have an index on `email`, so I think the database needs a bigger instance. Can you investigate before we pay for that?

# Context

Schema (PostgreSQL 15):

```sql
CREATE TABLE users (
  id          bigserial PRIMARY KEY,
  email       text NOT NULL,
  full_name   text NOT NULL,
  password_hash text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ix_users_email ON users (email);
```

Query, generated by the application (the code is `db.Users.Where(u => u.Email.ToLower() == email.ToLower())`):

```sql
SELECT id, full_name, password_hash FROM users WHERE lower(email) = lower($1);
```

Plan from `EXPLAIN (ANALYZE)` on a production-like copy, for one email address:

```
Seq Scan on users  (cost=0.00..201452.00 rows=1 width=90) (actual time=2140.8..2140.9 rows=1 loops=1)
  Filter: (lower(email) = 'ana@example.com'::text)
  Rows Removed by Filter: 7999999
Execution Time: 2141.1 ms
```

Facts:

- The table has about 8 million rows. The database CPU is low outside of these lookups.
- Emails are compared case-insensitively on purpose, since users type them in different cases. The application lower-cases on input in some places but not in all.
- Emails must be unique ignoring case, but no constraint enforces this today.
- The table receives about 20 inserts per minute and few updates.

# Expected Behavior

The agent reads the plan: the query scans all 8 million rows and applies the function to each, which explains the time. The existing index is on `email`, but the query filters on `lower(email)`, which is a different expression, so the index cannot be used for it. The database is not underpowered, as the query does unnecessary work, and a bigger instance would make a bad plan faster but not fix it. The agent uses `database-sql` as the core and `performance` for the slow query. `debugging` is not needed, since the schema, query and plan show the cause, and the agent does not run broader investigations. It presents fixes with their trade-offs: an index on the expression `lower(email)`, which serves the query as written and adds small write cost at the stated insert rate; or storing and comparing a normalized form (lower-cased on write), with changes to the application and existing data; or a case-insensitive column type, with its own implications. It points out that uniqueness ignoring case is a related correctness issue, since a unique index on `lower(email)` would both speed up the lookup and enforce the rule, but creating it will fail if case-variant duplicates already exist, so it recommends checking for them with a read-only query first. It notes creating the index on a production table should be done in a way that does not block writes (PostgreSQL-specific), and that the gain should be verified by re-running the plan and timing, without promising a number. It states the remediation changes the schema and asks for authorization before anything is applied, and does not claim to have run anything.

# Important Checks

- The function on the column is identified as the reason the existing index is unused.
- The "bigger instance" theory is addressed with evidence from the plan.
- The fix options are compared, including write cost at the stated rate.
- The uniqueness and case-variant duplicate issue is identified, with a read-only check first.
- PostgreSQL-specific points (expression index, non-blocking build) are identified as such.
- Verification is by re-running the plan and timing, with no promised number.
- Schema changes are proposed with authorization, not executed.
- The agent does not run a broad investigation when the cause is visible.
- No invented plan output or timings.

# Failure Conditions

- Agreeing to scale up the instance.
- Adding another index on `email` alone and expecting it to help.
- Missing that the function prevents the index from being used.
- Changing the application to compare without lower-casing, without noting the case-insensitivity requirement.
- Creating a unique index without checking for existing duplicates.
- Claiming a specific speedup or showing an invented new plan.
- Executing or claiming to execute DDL.
- Invoking debugging and other skills with no need.

# Notes

Either an expression index or normalized storage can be a good answer. The case tests reading the plan correctly and respecting the case-insensitivity requirement.
