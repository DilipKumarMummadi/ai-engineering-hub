# Changelog

## Unreleased

## 1.1.0 - 2026-10-04

### Changed
- MCP integration layer corrected. The Claude Code GitHub token prompt is kept, and Atlassian and PostgreSQL now get the same optional install-time inputs in `.claude-plugin/plugin.json` (`atlassian_auth` as a full Authorization header value, `postgres_database_uri` passed to the server through a pinned `sh -c` wrapper). All three are optional and sensitive; leaving one empty falls back to the user's own client or shell configuration (`DATABASE_URI` for PostgreSQL). The validator and its tests accept only `${user_config.KEY}` references to sensitive options and reject literal credentials, `${...}` expansion in the wrapper, and overrides that change a server's URL, type or pinned command. Added the seven-state MCP State Model (documented, declared, configured, connected, runtime visible, tool available, callable), nine availability states with exact messages, and a capability-resolution procedure (`docs/mcp-capability-registry.md`, `docs/mcp-integration-strategy.md`), the `design` (Figma) capability as optional Design evidence, installation and re-discovery behavior, and a runtime validation record (`docs/mcp-clients/claude-code.md`). Requirement, database, PR intelligence and test-planning agents resolve capabilities by operation and report precise states (both platforms). 30 new qualitative cases in `evals/mcp-integration/`, judged PASS, NEEDS_IMPROVEMENT or FAIL, written but not run. No custom MCP, no credential storage, no change to Requirement Intelligence, the readiness gate or Engineering Memory (still specification-only).

### Added
- Interactive Requirement Discovery (extends Phase 7, no new agent, command or readiness system): `/requirement` now starts an interactive session with requirement-type detection, dynamic checkpoints (baseline, type-specific and discovered), one highest-priority question at a time with options, answers and user-written context folded back in, whole-requirement re-analysis after each cycle, conflict handling (Conflict Detected, user decides), a conversation-held requirement workspace, and an `inspect` mode. Checkpoints carry status, importance and resolution (`RESOLVED_FROM_JIRA`, `RESOLVED_BY_USER`, `CONFIRMED_BY_USER`, `INFERRED`, `REQUIRES_CONFIRMATION`). Extended skill, agent, commands, feature-development stage 1 (not-ready result lets refinement continue; READY waits for user confirmation), and the readiness, confidence, traceability and specification documents. New `docs/interactive-requirement-discovery.md`, 27 interactive evaluation cases and a synthetic pilot fixture in `evals/requirement-intelligence/`. No live Jira session was used to produce the fixture.
- Phase 7 Requirement Intelligence and implementation readiness: the `requirement-intelligence` skill (now 14 skills), `requirement-intelligence-agent`, and the `/requirement` command (`analyze`, `refine`, `readiness`, `update`; Claude `.claude/commands/requirement.md`, Copilot `.github/prompts/requirement.prompt.md`, exposed by the Claude Code plugin). A requirement, for example Jira `BR-7368`, is read through the existing `requirements-tracking` capability, analyzed against repository evidence, Project Context and (where entries exist) Engineering Memory, and assessed for Requirement Readiness (`READY`, `NEEDS_CLARIFICATION`, `BLOCKED`) and qualitative Confidence (`HIGH`, `MEDIUM`, `LOW`, `UNKNOWN`), with no numeric scores. A ticket is updated only after explicit approval of the exact difference, then re-read and reassessed. Implementation gate: `/feature <key>` stops at stage 1 with `Implementation blocked.` unless `READY`; `READY` never starts implementation; manual `/feature` requirements go through the same gate. The requirement ID is carried through workflows, PR preparation and PR Intelligence. New documents: requirement readiness specification, gate, policy, confidence and traceability, plus a capability matrix in the Requirement Intelligence Specification. Updated: feature-development (stage 1, no renumbering), bug-fix, api-change, database-change, e2e-test-creation, pr-preparation, `workflow-common`, `pr-intelligence-agent` (Requirement → Change → PR), MCP capability registry, registries, user guide, README, architecture. Evaluations in `evals/requirement-intelligence/` and six Jira cases in `evals/integration/`. No custom Jira MCP, no credentials, no requirement database, no new infrastructure. Engineering Memory remains specification-only; the agent reports it unavailable instead of inventing entries.
- Phase 4 orchestration workflows: the seven workflows (feature-development, bug-fix, api-change, database-change, e2e-test-creation, pr-preparation, production-incident) are documented with objective, trigger, inputs, stages, agents, skills, MCP capabilities, outputs, safety, human checkpoints and failure handling in `docs/workflows.md`, `docs/workflow-registry.md`, `docs/workflow-specification.md`, `docs/architecture.md` and the README, with the shared architecture, dynamic skill routing and `docs/workflow-common.md`. New workflow commands `/feature`, `/bug-fix`, `/api-change`, `/database-change`, `/e2e` and `/pr-prep` (Claude `.claude/commands/`, Copilot `.github/prompts/`) that route to exactly one workflow and authorize no migrations, deployments, merges or production changes; `/incident` remains the production-incident entry. The hub validator now accepts a command that names exactly one existing agent or one existing workflow. No new skills, agents, MCP servers or frameworks, and no Grafana MCP.
- Phase 3 external MCP capability layer (documentation): capabilities `source-control`, `requirements-tracking`, `database`, `browser-automation` and `cloud-platform` (Azure, registered, not bundled), each with purpose, providers, consumers, authentication and configuration owner, input, output, missing-capability behavior and security notes in `docs/mcp-capability-registry.md`; provider-resolution diagram, availability model and evidence classes. Three-layer runtime configuration and database safety rules in `docs/mcp-runtime-configuration.md`. New `docs/mcp-setup-guide.md`. Jira Requirement Alignment section in the PR Intelligence Specification. The Hub builds no MCP server, implements no authentication and stores no credentials. Claude Code's `userConfig.github_token` is documented as a client-specific exception. Observability MCP access is deferred to a later phase.
- `/review-pr <PR URL | number>`: an entry variant of `/pr-intelligence` that retrieves a pull request through the `source-control` capability (GitHub MCP is one provider) and returns a `# PR Review` with a READY, NEEDS_CHANGES or NEEDS_INFORMATION recommendation. Agent changes in `pr-intelligence-agent` (PR reference handling, local-versus-PR rule, missing-capability behavior, PR review output form). `docs/mcp-capability-registry.md`, runtime-flow documentation, and evaluation cases (`evals/pr-intelligence/mcp/`). The Hub handles no credentials and adds no MCP server.
- `/context generate | inspect | drift`: a tool command (Claude `.claude/commands/context.md`, Copilot `.github/prompts/context.prompt.md`) that runs the existing Project Context Generator and drift detector on the current repository. Exposed by the Claude Code plugin manifest. The validator allows it as the one tool command. Documentation updates, fixture tests (`scripts/project-context/tests/test_context_command.py`) and evaluation cases (`evals/project-context-command/`). No new generator and no `ai-hub` executable.
- MCP runtime configuration model: `docs/mcp-registry.md`, `docs/mcp-runtime-configuration.md`, `docs/mcp-clients/` (Claude Code, GitHub Copilot CLI). `mcp.json` is static definitions only (static definitions only); `env` and `headers` are rejected by the validator. Earlier plugin MCP configuration: root `mcp.json` (Agent Plugins 1.0.0 schema) connecting existing GitHub (read-only), Atlassian (Jira/Confluence), Figma, Postgres (read-only) and Playwright servers, with pinned package versions, `.claude-plugin/plugin.json` to bridge it to Claude Code, `docs/mcp-setup-guide.md`, a Claude Code `userConfig` prompt for the GitHub token, and validator checks that reject literal credentials. No server code and no credentials are shipped.
- MCP integration strategy (`docs/mcp-integration-strategy.md`): the Hub consumes existing MCP servers for external access and keeps all engineering reasoning. Usage rules, capability mapping, an "External tools (optional)" note in each agent's Tool Usage and an "External sources (optional)" note in each workflow (both platforms), architecture and plugin documentation updates, and evaluation cases (`evals/mcp-integration/`). No MCP server, tools or `mcp.json` were added.
- Agent Plugin packaging (Agent Plugins 1.0.0): `plugin.json`, portable `skills/` (13 skills), `com.github.copilot/` namespace note, the plugin `README.md`, `docs/plugin-architecture.md`, a plugin validator with tests (`scripts/validate-plugin/`) and evaluation cases (`evals/plugin-packaging/`). Additive; no MCP.
- PR Intelligence: `pr-intelligence-agent`, the `/pr-intelligence` command, the `pr-intelligence` workflow, the PR Intelligence Specification (`docs/pr-intelligence-specification.md`) and evaluation cases (`evals/pr-intelligence/`). It orchestrates change intelligence, code review and only the relevant supporting analyses, and reports Ready, Needs Changes or Needs Information. It recommends only; it never approves or merges.
- Change Intelligence: the `change-intelligence` skill, `change-intelligence-agent`, the `/change-impact` command, the Change Intelligence Specification (`docs/change-intelligence-specification.md`) and evaluation cases (`evals/change-intelligence/`). Analysis only.
- Change Intelligence is used inside existing workflow stages where a change spans several areas: pr-preparation (stage 1), feature-development (stage 4), api-change (stage 4), database-change (stage 5) and bug-fix (stage 6). No stage was added or renumbered.
- Project Context Consumption standard (`docs/project-context-consumption.md`): how agents and workflows discover, validate and use `PROJECT-CONTEXT.md`
- A Project Context section in all seven agents and all seven workflows, on both platforms. It lists only the relevant topics and references the standard. Agent behavior changes: agents now check for a context, validate claims against repository evidence and report material conflicts. Behavior without a context is unchanged.
- Agent Specification section 4A and Workflow Specification section 3A, and a Project Context section in the required agent and workflow structure
- Context-aware agent evaluation cases (`evals/integration/context-aware-agents/`)
- Initial AI Engineering Hub repository structure
- Claude Code integration directories
- GitHub Copilot integration directories
